# DB Operator 동작·성능 검증 리포트

이 문서의 수치는 기존 자체 복제 프로필에서 측정했습니다. GCP DMS 공통 API 경로의 처리량·전환 시간 측정값은 아닙니다.

검증일: 2026-11-05. 자체 운영 PostgreSQL 18과 DynamoDB Local을 사용한 로컬 Docker 시험입니다.

성능 수치는 `1e317e9`의 정적 Registry 구성에서 측정했습니다. 이후 추가한 동적 앱 등록·Secret 조회 경로의 성능을 나타내지는 않습니다.

## 결과

API와 Worker를 한 backend 컨테이너에 넣고, PgBouncer는 별도 컨테이너 하나로 유지했습니다. 이 구성에서 초기 복사, CDC, 대상 전환, 대상의 새 쓰기, 역방향 롤백과 원본의 새 쓰기를 확인했습니다.

backend와 PgBouncer의 자원을 합계 0.5 CPU·1 GiB로 제한했을 때 주문 처리량은 1,471.01 TPS였습니다. 상태 조회는 초당 278.03건이었고 측정 중 오류는 0건이었습니다. 짧은 로컬 시험 결과이며 실제 ECS의 처리량이나 운영 용량을 보장하지 않습니다.

## 실행 구조

```text
ECS Task 설계: 0.5 vCPU / 1 GiB / desiredCount=1
├─ backend 컨테이너
│  ├─ API 프로세스: 요청 접수·상태 조회
│  └─ Worker 프로세스: 복제·전환·롤백 실행
└─ PgBouncer 컨테이너: 앱의 상시 DB 접속점

앱 → PgBouncer → 원본 또는 대상 PostgreSQL
API·Worker·PgBouncer → DynamoDB: 작업·경로 상태
```

로컬 시험에서는 위 두 컨테이너의 CPU·메모리 한도를 Docker로 적용했습니다. PostgreSQL, DynamoDB Local, 부하 생성기는 이 한도 밖에서 실행했습니다. 실제 ECS에는 배포하지 않았습니다.

상태는 DynamoDB에 저장합니다. 실행 의도와 HELD 경로를 외부 변경 전에 함께 기록합니다. 변경 결과를 확인하지 못하면 UNKNOWN으로 멈춥니다. Worker 잠금은 자동 만료하지 않으며 강제 종료 뒤에는 이전 실행기의 종료 확인과 명시적 잠금 복구가 필요합니다.

## 측정 조건

| 항목 | 조건 |
|---|---|
| 호스트 | Apple M4, macOS 27.2, OrbStack ARM64 Docker |
| Docker VM | CPU 10개, 메모리 약 7.82 GiB |
| 데이터 계층 | PostgreSQL 18, PgBouncer 1.25.1, DynamoDB Local |
| 초기 데이터 | 주문 50,000건, 상품 128개 |
| 주문 1건 | 임의 상품의 재고 UPDATE + 고유 주문 INSERT + COMMIT |
| 동시 부하 | 상태 조회 클라이언트 8개 + PgBouncer를 통한 DB 연결 16개 |
| 실행 시간 | 구성마다 6초씩 3회, 요청 완료 뒤 다음 요청을 보내는 폐쇄형 부하 |
| 복제·암호화 | 부하 중 PostgreSQL 논리 복제 실행, 클라이언트 TLS 사용, 시험용 DB 측 TLS 미사용 |

처리량과 지연은 각 회차 측정값의 중앙값입니다. P95도 회차별 P95의 중앙값이며 전체 요청을 합친 P95는 아닙니다. API 수치는 관리용 상태 조회입니다. 주문 수치는 HTTP 앱을 거치지 않은 DB 트랜잭션 처리량입니다.

## 처리량과 지연

| 구성 | 상태 조회/초 | 조회 P95 | 주문 TPS | 주문 P95 | 오류 |
|---|---:|---:|---:|---:|---:|
| API·Worker 분리, CPU 제한 없음 | 370.63 | 31.59 ms | 2,778.06 | 8.81 ms | 0 |
| API·Worker 통합, CPU 제한 없음 | 402.94 | 29.69 ms | 2,872.59 | 8.43 ms | 0 |
| 통합, 합계 0.5 CPU·1 GiB 제한 | 278.03 | 78.24 ms | 1,471.01 | 62.47 ms | 0 |

첫 두 구성은 같은 Python 상태 검사 조건에서 비교했습니다. 3회의 짧은 측정만으로 통합 구성의 성능 우위를 확정할 수는 없습니다.

제한 구성은 backend에 0.375 CPU·768 MiB, PgBouncer에 0.125 CPU·256 MiB를 적용했습니다. 상태 검사도 `curl /live`와 `pg_isready`를 10초 간격으로 실행하도록 바꿨습니다. 첫 두 구성과 검사 방식이 달라 직접적인 자원 효율 비교에는 사용할 수 없습니다. 컨테이너 메모리 합계의 최대 표본값은 249.44 MiB였습니다. 메모리는 3회 표본이며 실제 최대 사용량은 확인하지 않았습니다.

## 전환과 롤백

부하 요청이 모두 끝난 뒤 업무 정지 근거를 만들고 전환했습니다. 아래 시간에는 API 요청, Worker 실행, 결과 확인과 첫 쓰기가 포함됩니다.

| 구성 | 계획 등록부터 초기 복사 READY까지 | QUIESCE 준비부터 대상 첫 쓰기까지 | 롤백 QUIESCE 준비부터 원본 첫 쓰기까지 |
|---|---:|---:|---:|
| API·Worker 분리, CPU 제한 없음 | 1.42초 | 20.89초 | 3.33초 |
| API·Worker 통합, CPU 제한 없음 | 3.47초 | 19.63초 | 3.18초 |
| 통합, 합계 0.5 CPU·1 GiB 제한 | 1.80초 | 3.52초 | 3.89초 |

초기 복사 시간에는 계획 등록·PREPARE·START_SYNC·READY 확인이 포함됩니다. 순수 데이터 복사 시간은 아닙니다. 전환·롤백은 구성마다 한 번 측정했습니다.

각 구성에서 발생한 변경량이 다릅니다. CPU 제한 없는 구성은 같은 부하 시간에 더 많은 주문을 처리했습니다. 이 결과만으로 컨테이너 통합이나 CPU 제한이 전환 시간을 줄였다고 판단할 수 없습니다. 단계별 병목도 측정하지 않았습니다. 전환 중 쓰기를 정지하므로 무중단 쓰기를 확인한 결과는 아닙니다.

제한 구성의 최종 주문은 76,465건이었습니다. 고유 주문 수도 76,465건이었고 재고 합계는 127,923,535개였습니다. 초기 재고 128,000,000개에서 주문 수를 뺀 값과 일치했습니다. 대상에서 쓴 주문의 원본 복귀와 sequence 증가를 확인한 뒤 FINALIZE했습니다.

## 발견한 문제와 수정

| 문제 | 수정·확인 |
|---|---|
| 상태 캐시 만료 뒤 동시 조회가 HTTP 409 발생 | 같은 API 프로세스의 관측 갱신을 묶고 대기 요청이 캐시를 다시 읽도록 수정. 동시 조회 회귀 검사 통과 |
| 작은 CPU 한도에서 Python 상태 검사 시간 초과 | backend는 `curl`, PgBouncer는 `pg_isready` 사용. 같은 자원 한도로 시작·부하·전환·롤백 완료 |

현재 소스의 단위 검사 43개와 조회·캐시·상태 경합 관련 통합 검사 5개가 통과했습니다. Ruff 검사·포맷 검사, wheel·sdist·Docker 빌드도 통과했습니다. 패키지와 이미지의 Python 구현 파일 13개 및 `contract.json`이 현재 소스와 일치했습니다.

Docker에서 API 종료, Worker 강제 종료, backend SIGTERM, TARGET·OPEN 재시작, HELD 재시작도 확인했습니다. Worker 강제 종료 뒤에는 잠금을 보존했습니다. 상세 실행 기록과 이전 전체 검사 130개의 시점은 [검증 기록](verification.md)에 있습니다. 130개 전체 검사는 backend 통합 전 결과이며 현재 소스의 전체 재검사 결과로 합산하지 않습니다.

## 적용 판단

해커톤의 다음 통합 시험은 backend·PgBouncer 두 컨테이너 구성으로 진행할 수 있습니다. 성능 수치는 이번 로컬 조건의 기준값으로 사용합니다.

실서비스 투입 판단에는 실제 ECS·IAM·공인망·DB 측 TLS 검증과 장시간 부하 검사가 더 필요합니다. 100,000 RPS, 클라우드 간 지연, 대용량 데이터, 장애 중 처리량과 고가용성은 확인하지 않았습니다. 공개 DNS·허용 IP 자동 갱신도 구현하지 않았습니다.

이번 시험은 자체 운영 PostgreSQL의 논리 복제를 사용했습니다. 클라우드 DMS 성능 시험이 아닙니다. DMS CLI의 확인·시작·상태 조회·실행 기록은 구현했지만 관리형 DMS의 전환·롤백은 공통 API에 연결하지 않았습니다. RDS·Cloud SQL 전체 이전이 검증됐다는 의미로 사용하면 안 됩니다.

측정값은 [성능 근거 JSON](performance/2026-11-05.json)에 있습니다. 자격 증명과 로컬 설정은 제외했습니다. 실행·검사 방법은 [README](../README.md), 배포 조건은 [ECS 가이드](../deploy/ecs/README.md)를 따릅니다.
